# ورقة قرار — غرفة التحكّم عبر تيليجرام (610)

**الحالة: مسجَّلة · لم تُنفَّذ**
**التاريخ: 2026-08-01**
**القرار من: محمد رزوق**

---

## القرار

**تيليجرام هو غرفة التحكّم — قناة واحدة تكفي الآن.**

**والغرض ليس التنبيه: هو إدارة النظام كاملًا من خارج المنزل.**

**ما يجب أن يمكّنه:**

```
قراءة السجلّات
معرفة صحّة النظام
معرفة أن النظام حيّ
إدارة المخاطر
توجيه اتجاه العمل — شراء فقط مثلًا
تنفيذ صفقة من تحليل شخصي والنظام يدير مخاطرها
```

---

## نتيجة الفحص — والنتيجة تغيّر ترتيب العمل

**فُحص كل ما تحتاجه غرفة التحكّم مقابل ما يُنشر فعلًا:**

### كل ما تريد قراءته موجود ويُنشر

| ما يُقرأ | من |
|---|---|
| السجلّات وملخّص الأخطاء | 761 |
| صحّة النظام | 851 |
| نبضة الحياة | 3 |
| حالة المخاطر | 500 |
| المراكز الحيّة | 609 |
| الأداء والمحفظة | 650 |

### وكل ما تريد التحكّم به غير موجود

| الأمر | الحدث | الحالة |
|---|---|---|
| إعادة تشغيل المفتاح | `risk.kill_switch.reset_requested` | **لا ينشره أحد** |
| توجيه الاتجاه | `strategy.direction.forced` | **غير موجود إطلاقًا** |
| صفقة يدوية | `execution.manual.requested` | **غير موجود إطلاقًا** |
| إيقاف زوج | `risk.halt.pair` | **غير موجود** |
| إيقاف حساب | `risk.halt.account` | **غير موجود** |

**فالمشكلة ليست القناة. المشكلة أن النظام لا يقبل أمرًا من أحد.**

**ولهذا: بوّابة الأوامر تُبنى أولًا، وتيليجرام بعدها.**

## لماذا تيليجرام لا موقع — الآن

| | تيليجرام | موقع |
|---|---|---|
| **بلا فتح منفذ** | **يتّصل خارجًا وحده** | يحتاج IP عامًّا أو نفقًا |
| **من أي بلد وأي شبكة** | **نعم** | يحتاج اتصالًا مستقرًّا |
| **بيانات ضعيفة** | **يعمل** | يتعثّر |
| **يبادر بالإخبار** | **نعم** | لا، إلا بإشعار |
| قراءة سجلّ طويل | نصّ محدود | **أفضل** |
| نموذج بحقول | أزرار | **أفضل** |
| الأمان | مغلق على معرّفك | يحتاج شهادة ومصادقة |

**السبب الحاسم: الجهاز خلف راوتر منزلي، والمالك خارج المنزل.**

**والموقع يبقى للمكتب — واللوحة (850) تخدمه أصلًا.**

**ولا واحد منهما يمسّ النواة.**

## البنية — ثلاث طبقات لا واحدة

```
تيليجرام  ←→  610 القناة  →  بوّابة الأوامر  →  الأحداث  →  الذرّات
                                    ↑
                              اللوحة لاحقًا
```

**والفصل مقصود:** 610 قناة، والقناة لا تقرّر.

**وبوّابة الأوامر مشتركة:** حين تُضاف اللوحة أو أي قناة أخرى، **لا يُعاد بناء منطق الأوامر.**

## القطعة الأولى: 610 — نسخة جديدة من نسختين

**تُبنى من الحالي أساسًا، ويُنقل إليها من القديم ما ينقصها.**

### ما يبقى من الحالي — بنيته أمتن

```
ConnectionSupervisor   إشراف على الاتصال وإعادته
PollingEngine          محرّك سحب منفصل بمعالجة أخطاء
answerCallbackQuery    يردّ على الأزرار فلا تعلّق
RateLimiter            حدّ معدّل الإرسال
_render_view           عرض منظّم
```

### ما يُنقل من القديم — وهو الوظيفة المفقودة

```
_parse_command          يفهم "/halt" و"/reset" مع الوسائط
telegram.command.received   ينشر أمرك للنظام
telegram.connected · disconnected   يعرف النظام أن قناته حيّة
```

**والحالي ينشر `telegram.error` و`telegram.ignored` فقط — يعرض ولا يأمر.**

### ما يُصحَّح

```
risk.alert  →  tools.alert.raised
```

**610 يسمع `risk.alert`، و766 ينشر `tools.alert.raised`.**

**فتيليجرام صامت عن المخاطر اليوم — والسبب اسم لا يتطابق، لا عطل في أيّهما.**

---

## القطعة الثانية: بوّابة الأوامر — ذرّة جديدة

```
تسمع:   telegram.command.received   (ولاحقًا: أوامر اللوحة)
تفحص:   الهوية · الصلاحية · معقولية الأمر
تنشر:   الحدث المناسب
```

**وتحتفظ بسجلّ: من أمر، بماذا، ومتى، وما نتيجته.**

**ولماذا ذرّة مستقلّة لا داخل 610:**

- القناة قد تتعدّد — اللوحة لاحقًا، وربّما إيميل
- **منطق الصلاحيات في مكان واحد** لا في كل قناة
- 610 يصير قابلًا للاستبدال بلا فقدان التحكّم

## الأوامر — ثلاث فئات

### ① قراءة — بلا خطر

```
/status      حالة النظام: كم ذرّة تعمل، وكم سقطت
/health      صحّة الأقسام
/alive       آخر نبضة من النظام والجسر
/risk        حالة المخاطر والحدود والانكشاف
/positions   المراكز الحيّة
/pnl         الأداء اليومي والجلسة
/log         آخر الأخطاء
```

**تُنفَّذ فورًا. لا تأكيد.**

### ② تحكّم — يحتاج تأكيدًا

```
/halt              إيقاف شامل — كل الذرّات، والنواة تبقى
/halt_account X    إيقاف حساب — كل أزواجه
/halt_pair X Y     إيقاف زوج — في حسابه فقط
/resume ...        إعادة تشغيل المستوى المقابل
/direction buy     توجيه: شراء فقط
/direction both    عودة للطبيعي
```

**وثلاثة مستويات الإيقاف من ورقة تعدّد الحسابات.**

**التأكيد إلزامي:** الأمر يُعرض ملخَّصًا، ويُنفَّذ بضغطة ثانية.

### ③ تنفيذ يدوي — الأخطر

```
/buy  SYMBOL SIZE SL TP
/sell SYMBOL SIZE SL TP
```

**قرار المالك: الصفقة اليدوية ضمن النظام، والنظام يدير مخاطرها.**

**فالأمر لا يذهب إلى المنصّة مباشرة، بل يمرّ بالمسار الكامل:**

```
/buy  →  execution.manual.requested
      →  508 يفحص الانكشاف
      →  516 يفحص المفتاح
      →  551 يبني الأمر — وقد يصحّح الحجم
      →  553 يرسله
```

**فإن كان الحجم يخرق حدّ المخاطرة، يُرفض أو يُصحَّح — ويُعلَن السبب.**

**ولماذا هذا التصميم:** أمر بحجم خاطئ من هاتف = خسارة حقيقية بلا زرّ تراجع.
**والمسار الكامل يجعل النظام حارسًا حتى على أوامر مالكه.**

## الصلاحيات

| الفئة | من له الحقّ |
|---|---|
| قراءة | كل معرّف مسموح |
| تحكّم | **المالك وحده** |
| تنفيذ يدوي | **المالك وحده + تأكيد ثانٍ** |

**وأي أمر من معرّف غير مسموح يُسجَّل ويُهمَل — لا يُردّ عليه.**

---

## ما يبادر به تيليجرام بلا طلب

**القناة تُخبر، لا تنتظر السؤال:**

```
النظام سقط أو صمت أكثر من الحدّ
المفتاح انقلب — وأي مستوى
حدّ خسارة بلغ
الجسر انقطع أو المنصّة فقدت الاتصال
صفقة فُتحت أو أُغلقت
انحراف مراكز — مركز تحمله المنصّة ولا يعرفه النظام
```

**والتقرير اليومي في وقت محدَّد.**

---

## ما لم يُحسم

| البند | السؤال |
|---|---|
| مهلة التأكيد | كم ثانية قبل أن يسقط الأمر غير المؤكَّد؟ |
| `/direction buy` | يُطبَّق على كل الحسابات أم حساب بعينه؟ |
| الصفقة اليدوية | هل تُقيَّد على استراتيجية أم تُعزل عن قياس الأداء؟ |
| صمت النظام | كم ثانية قبل أن يُنذر تيليجرام؟ |
| فقدان تيليجرام نفسه | إن انقطعت القناة، هل يُنذر النظام بطريقة أخرى؟ |

## الترتيب

1. **بوّابة الأوامر** — الذرّة الجديدة، وبدونها القناة صمّاء
2. **610 الجديد** — من الحالي أساسًا، ومن القديم `_parse_command` والنشر
3. **تصحيح `risk.alert`** — سطر واحد يُنهي صمت المخاطر
4. **أوامر القراءة** — بلا خطر، وتُثبت أن الحلقة تعمل
5. **أوامر التحكّم** — بالتأكيد الإلزامي
6. **التنفيذ اليدوي** — آخر شيء، بعد أن يستقرّ ما قبله

**النواة.** لا تيليجرام ولا اللوحة يحتاج فتحًا.
