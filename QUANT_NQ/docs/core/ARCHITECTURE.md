# معمارية النواة — QUANT_NQ Core V1.4.0

> **الوثيقة الحاكمة**: `ATOM_CONSTITUTION_V2.0.md`. عند أي تعارض بين ما
> هنا وبين نص الدستور، **الدستور هو الفيصل** (المادة 50).

---

## 1. القاعدة الذهبية

> إذا احتجت لفتح أي ملف داخل `core/` بسبب إضافة أو حذف أو نقل أو ترقية
> ذرة — فهذا **دليل خلل تصميم في الذرة**، وليس نقصًا في النواة
> (المادة 41).

هذه ليست توصية أخلاقية. منذ V1.4.0 صارت قيدًا تقنيًا مفروضًا:
`core/CORE.lock` يحمل بصمة تشفيرية لكل ملف داخل النواة، و`CI` يرفض أي
تغيير فيها. راجع القسم 9.

## 2. ما هي النواة، وما ليست

النواة **حاضنة تسيير** فقط (المادة 97). تفعل أربعة أشياء لا خامس لها:

1. **تكتشف** الذرات بالمسح المتكرر بحثًا عن `manifest.yaml`.
2. **تسيّر** دورة حياتها: Initialize → Start → Running → Stop → Shutdown.
3. **تقدّم خدمات عامة**: ناقل أحداث، سجل، مقاييس، لوغر، لقطات حالة.
4. **ترصد** الصحة وتوثّق الحالة.

وما ليست:

| ليست | لأن |
|---|---|
| نظام تداول | المادة 95/97 — لا معرفة بأسواق أو صفقات أو وسطاء |
| محرك استراتيجيات | المادة 98 — منطق الأعمال يعيش في الذرات حصرًا |
| مكتبة دوال مساعدة | المادة 96 — لا سلة مهملات برمجية |
| طرفًا يعرف ذرة بعينها | المادة 9/47 — لا اسم ولا رقم ذرة مكتوب في الكود |

اختبار `test_constitution_compliance.py` يفرض هذه الحدود آليًا: يفحص كود
النواة التنفيذي (بعد تجريد التوثيق والتعليقات) بحثًا عن أي مفردة تداولية
أو أي مقارنة بمعرّف ذرة بعينها، ويكسر البناء عند أول خرق.

## 4. دورة الإقلاع

```
scan(atoms/)                    اكتشاف كل manifest.yaml بأي عمق
   ↓
validate                        AtomManifest + config ضد config_schema
   ↓
graceful degradation            استبعاد كل ذرة غير قابلة للحل، تدريجيًا
   ↓
resolve                         ترتيب طوبولوجي (Kahn، لا عوديّة)
   ↓
instantiate                     تحميل entrypoint ديناميكيًا
   ↓
initialize → start              لكل ذرة، بمهلة قصوى
   ↓
watch                           تسليم الذرة لـ Health Manager
```

### 4.1 سياسة الفشل — المادة 21 (تصحيح جوهري في V1.4.0)

نص المادة صريح: حقل `critical` **«لا يوقف النواة إطلاقًا»**؛ أثره أن
الذرة الحرجة نفسها تُمنع من التشغيل أو تُوقف، **بينما يستمر Core**.

في V1.3.0 كان `Bootloader.boot()` يُرجع مبكرًا عند أول فشل لذرة حرجة،
فيحرم كل الذرات التالية في ترتيب الإقلاع من التشغيل. هذا خرق مباشر
للمادة 21 وللمادة 81.

**السلوك المعتمد الآن:**

| الحدث | النتيجة |
|---|---|
| ذرة غير حرجة تفشل | تُستبعد وحدها، الإقلاع يكمل |
| ذرة **حرجة** تفشل | تُستبعد وحدها، الإقلاع يكمل، ويُسجَّل السبب في `abort_reason` و`success=False` |
| ذرة حرجة باعتمادية مفقودة/حلقة/إصدار غير متوافق | تُستبعد وحدها، الإقلاع يكمل |

`success=False` صار يعني **«فشلت ذرة حرجة»**، لا **«توقف النظام»**.
التقرير يخبر المشغّل بالحقيقة كاملة، والقرار التشغيلي (تنبيه بشري،
إيقاف مخطَّط) يعود لطبقة أعلى — لا للنواة.

## 5. ناقل الأحداث — ضمانات العزل

المادة 89 تمنع أي ذرة «تالفة أو معطلة أو **بطيئة**» من التأثير على بث
الأحداث. الضمانات المنفَّذة:

| الضمان | التنفيذ |
|---|---|
| استثناء مشترك لا يمسّ غيره | `asyncio.gather(..., return_exceptions=True)` |
| مشترك **بطيء أو معلّق** لا يجمّد الناقل | `asyncio.wait_for` لكل معالج، `dispatch_timeout_s` |
| مشترك لا يعدّل ما يراه غيره | كل مشترك يستلم `dict(base)` مستقلة |
| حمولة المستدعي لا تُعدَّل | نسخة تُبنى قبل أي حقن |
| المصدر يصل للمشترك | `source` يُحقن تلقائيًا (المادة 31) |
| لا أثر بعد الإزالة | `unsubscribe_all` يحذف المفتاح كاملًا |

الحقول المعيارية المحقونة تلقائيًا: `source`, `trace_id`, `timestamp` —
تُحقن بـ `setdefault`، فالذرة التي تضبطها بنفسها تحتفظ بقيمها.

`trace_id` يُربط بـ `ContextVar`، فكل رسالة لوغ تصدر من داخل معالج
الحدث تحمل نفس المعرّف تلقائيًا، ويمكن تتبّع سلسلة كاملة عبر عدة ذرات.

## 6. الصحة وإعادة التشغيل

- كل ذرة تُراقَب بمهمة `asyncio` مستقلة، بإعدادات `health` من مانيفستها.
- `failure_threshold` فحوصات فاشلة متتالية ⇒ الذرة `UNHEALTHY` + حدث.
- `restart_on_failure` ⇒ `stop()` ثم `start()` مع backoff تصاعدي.
  **`shutdown()` لا تُستدعى إطلاقًا في دورة إعادة التشغيل** — هي مرحلة
  نهائية غير قابلة للعكس، وهذا هو سبب فصلها عن `stop()`.
- **فشل الفحص الصحي لا يوقف Core ولو كانت الذرة حرجة** (المادة 21/81):
  تنبيه `critical` + حدث `core.critical_atom.unhealthy`، والقرار لطبقة أعلى.
- ميزانية إعادة التشغيل **تتجدد** بعد استقرار مثبت (10 فحوصات صحية
  متتالية). بدون ذلك تُستهلك الميزانية مرة واحدة مدى عمر العملية،
  فتفقد الذرة حمايتها بعد شهور من التشغيل السليم.

## 7. الاكتشاف الحي (Runtime Discovery Engine)

المادة 14/46: إضافة أو سحب أو ترقية ذرة **لا تتطلب إعادة تشغيل النواة**.

```
فحص دوري (rescan_interval_s)  ─┐
POST /api/rescan               ─┼→  قفل واحد  →  فحص واحد فقط في كل لحظة
حدث core.system.rescan_requested┘
```

**عند التحميل الحي**، الذرة الجديدة تمر بنفس بوابات الإقلاع بلا تخفيف:
توافق `core_version` (المادة 20)، احترام `startup_mode` (فـ `manual`
و`lazy` تُكتشف ولا تُشغَّل)، حلّ الاعتماديات، **وترتيب تحميل يتبع
الاعتماديات لا المعرّف الرقمي**.

**عند فشل التحميل الحي**، الذرة تُطهَّر بالكامل — `stop`، `shutdown`،
إلغاء الاشتراكات، إلغاء المراقبة، إلغاء التسجيل — فلا تبقى سجلًا ميتًا
يمنع إعادة المحاولة بعد إصلاحها (المادة 11/15).

**عند السحب الحي**، التطهير مضمون **حتى لو رمت الذرة استثناءً** في
`stop()` أو `shutdown()`: سلوك ذرة سيئة لا يترك أثرًا في Registry ولا في
الناقل (المادة 15/86).

## 8. سياسة الأخطاء

مبدأ واحد: **لا يُسمح لخطأ في ذرة واحدة بإسقاط العملية** (المادة 81).

| الطبقة | السلوك |
|---|---|
| داخل الذرة | مسؤوليتها وحدها (المادة 27/82) |
| حدود Core | كل استدعاء لكود ذرة مغلَّف بـ `try` ومهلة |
| Journal | يسجّل، ولا يرتد استثناؤه إلى مسار الذرة |
| Bootloader | يستبعد ويواصل — لا يُجهض |
| Health Manager | يرصد ويوثّق ويعيد التشغيل — لا يُسقط |
| API | يبقى حيًا مهما فشلت الذرات |

## 9. تجميد النواة

النواة مختومة بـ `core/CORE.lock`: بصمة `SHA-256` لكل ملف، وبصمة جامعة
واحدة تمثل النواة كاملة.

```bash
python scripts/freeze_core.py verify     # يفشل عند أي تعديل
python scripts/freeze_core.py status     # عرض حالة الختم
python scripts/freeze_core.py freeze --reseal   # إعادة ختم متعمَّدة فقط
```

ثلاث طبقات حماية، كلها محلية بالكامل:

1. **الختم** — `CORE.lock` يكشف أي تعديل بايت واحد.
2. **الاختبار** — `test_core_is_frozen.py` يكسر أي تشغيل للاختبارات.
3. **حارس git** — `scripts/install_guard.sh` يركّب `pre-commit` يرفض
   أي commit يلمس `core/`. لا خادم، لا حساب، لا إنترنت.

أداة الختم تعيش في `scripts/` عمدًا: **الحارس ليس جزءًا من المحروس**،
وإلا استطاع تعديل واحد أن يزوّر الختم ويجتاز الفحص معًا.

### متى يجوز فتح الختم؟

فقط عند **إصدار معماري جديد** (المادة 1: V2, V3…) — لا لتشغيل ذرة، ولا
لإصلاح ذرة، ولا لتبسيط برمجة (المادة 99).

```bash
# 1. ارفع CORE_VERSION في core/__version__.py ووثّق السبب فيه
# 2. أعد الختم عمدًا
python3 scripts/freeze_core.py freeze --reseal
# 3. مرّر الـ commit متجاوزًا الحارس مرة واحدة
git commit --no-verify -m "Core V2.0.0 — <السبب المعماري>"
```

الختم لا يمنعك من شيء تقرره أنت. يمنع فقط أن يحدث التعديل **دون أن
تنتبه** — أن تفتح ملفًا في `core/` بعد ستة أشهر لتُرضي ذرة، وتنسى أنك
كسرت المبدأ الذي بنيت المنصة عليه.

## 10. ثبات العقد (المادة 64/65/67)

الترقية من V1.3.0 إلى V1.4.0 كانت **إصلاحًا داخليًا بحتًا**: كل ذرة
تعمل على 1.3.0 تعمل على 1.4.0 دون تعديل سطر واحد.

| ما تغيّر | ما لم يتغيّر |
|---|---|
| سياسة الفشل عند الإقلاع | توقيعات `AtomBase` |
| عزل ومهلة معالجات الأحداث | حقول `AtomContext` |
| حدود الذاكرة في Journal/Metrics | مخطط `AtomManifest` |
| ذرّية كتابة اللقطات | أسماء الأحداث القياسية |
| تطهير الموارد عند الفشل | رموز الأخطاء الرقمية |

هذا هو جوهر المادة 67: **العقد قانون ثابت، والتنفيذ قابل للاستبدال بصمت**.
